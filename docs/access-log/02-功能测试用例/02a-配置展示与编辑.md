> 覆盖：页面展示态 / 编辑态切换、白名单增删、保存与取消、名称归一与判重、敏感头拦截。

### ACL-01：Alert 提示与卡片标题展示

**功能模块**: 访问日志  
**优先级**: P1  
**用例编号**: ACL-01  
**生命周期**: 已通过（2026-11-16，`test_01`~`test_04` 定向 13/13）  
**设计依据**: 原型 `access-log.html` 顶部 Alert；`src/modules/AccessLog/index.vue`  
**OpenAPI**: `access-log.md` §1 数据模型（两段白名单语义）

#### 前置条件

- 以 `admin` 登录，进入「系统安全 → 访问日志」

#### 测试步骤

1. 观察页面顶部提示块与两张卡片
2. 悬停/展开提示块，核对提示内容是否包含采集语义

#### 预期结果

1. 顶部为蓝色 Alert（信息图标 + 加粗标题「访问日志 Header 白名单」），正文为说明与采集语义合并段落：按白名单采集请求头/响应头、单例全局配置且保存为整组全量替换、多值头逗号拼接、值超 2048 字节截断、空白名单 = 不采集、日志中名称为规范化形式
2. 标题中**不出现** `mod_access_pb3` 字样
3. 两张卡片标题分别为「请求头白名单（req_headers）」「响应头白名单（res_headers）」
4. 页面右上角仅一个「编辑」按钮，无「保存 / 取消」

### ACL-10：Header 名称格式校验

**功能模块**: 访问日志  
**优先级**: P1  
**用例编号**: ACL-10  
**生命周期**: 已通过（2026-11-16，`test_01`~`test_04` 定向 13/13）  
**设计依据**: UI `validateHeaderName` 与 `access-log.md` 字段合法性条件逐条对齐

#### 前置条件

- 编辑态

#### 测试步骤

1. 输入框留空直接点「添加」
2. 输入仅空白字符（如空格）后点「添加」
3. 输入超过 128 字节的名称（如 129 个 `a`）
4. 输入含非法字符的名称（如 `x id`、`x:id`、`x@id`）
5. 输入合法名称（如 `x-request-id`）后点「添加」

#### 预期结果

1. 空值 → 拦截，提示「Header 名称不能为空」
2. 纯空白 → trim 后为空，同样拦截
3. 129 字节 → 拦截，提示「Header 名称长度不能超过 128 字节」；128 字节可添加
4. 含空格 / 冒号 / `@` → 拦截，提示「Header 名称含非法字符（仅允许 RFC 7230 token 字符）」
5. 合法名称 → 正常加入 tag 容器

### ACL-13：后端 422 兜底与零变更

**功能模块**: 访问日志  
**优先级**: P1  
**用例编号**: ACL-13  
**生命周期**: 已通过（2026-11-16，`test_01`~`test_04` 定向 13/13）  
**设计依据**: 「负向用例必须带拒绝后 GET 回读零变更」约定；后端为最终边界  
**OpenAPI**: `access-log.md`：元素格式、归一去重、敏感头三类校验返回 422 `Param Illegal`

#### 前置条件

- 记录当前 `GET access-log/config` 的完整响应体作为基线
- 具备直接调用 OpenAPI 的能力（绕过前端）

#### 测试步骤

1. 直接 `PUT` 含 `Authorization` 的请求体
2. 直接 `PUT` 含归一去重项（`x-id` 与 `X-ID`）的请求体
3. 直接 `PUT` 含超 128 字节或非法字符名称的请求体
4. 每次失败后调 `GET` 核对

#### 预期结果

1. 三种非法请求均返回 `422`（`Param Illegal`），错误信息指明具体非法项
2. 每次失败后的 `GET` 响应体与基线完全一致（零变更）
3. 失败请求不写 `operation_log`（或仅记失败审计，不改变配置）

#### 补充说明

- 前端同样会拦截上述三类输入（见 ACL-10/ACL-11/ACL-12），本用例用于验证服务端兜底不被前端掩盖。
