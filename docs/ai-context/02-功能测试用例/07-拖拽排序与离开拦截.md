## 7. 拖拽排序与离开拦截

> 变更依据：`ai-gateway-web` 提交 `792bb73` 引入规则模块的「拖拽排序 + 未提交离开拦截 + 退出编辑模式二次确认」能力，本模块产品实现见 `src/modules/AIContext/index.vue`：
> - `:draggable="rulesMode === 'edit'"` 与 `@dragDrop="onRuleDragDrop"`（第 63~64 行）；

> - `onRuleDragDrop(startIndex, endIndex)`：`splice` 取出后按**目标原下标**插入，**不重新编号**（第 461~469 行）；

### AX-DR-02：拖拽到目标行落到目标行原下标

### AX-DR-03：列排序/列搜索激活时拖拽按源下标移动正确的行

**功能模块**: 列表与双模式
**优先级**: P1
**用例编号**: AX-DR-03
**设计依据**: `src/components/table/pageTable.vue:469-511`（`sortChange`）、`341-425`（`searchTable`）、`595-603`（`onDragDrop` 按 `pageSrcIndex` 派发源下标）

#### 前置条件

1. 已进入编辑模式，集合内存在 3 条以上压缩规则。
2. 「生效条件」列可排序（`sortable: 'custom'`）且可本地搜索（`searchable: true`）。

#### 测试步骤

1. 点击「生效条件」列头的倒序图标，记录排序后的可视顺序。
2. 拖拽**可视首行**到**可视末行**上，清空列搜索后读取表格顺序。
3. 另起一轮：在「生效条件」列搜索框输入能命中部分行的子串，仅展示命中行，重复步骤 2。

#### 预期结果

1. 列排序 / 列搜索只改变**展示顺序与可视行集合**，不改变 `rules` 数组本身（排序前后展示集合的排序副本相等）。
2. 拖拽时派发给 `onRuleDragDrop` 的是**源数组下标**：移动的行是「可视首行对应的规则」，落点是「可视末行对应的规则的原下标」，最终顺序按源下标推导（`moveRuleToIndex(基线, 可视首行源下标, 可视末行源下标)`）。
3. 负向对照：最终顺序**不等于**按「可视下标（0 与 可视末行下标）」派发时的结果，据此排除「按可视下标移动错行」的实现。
4. 场景具备判别力：排序态下**可视首行的源下标不为 0**，筛选态下**可视末行的源下标不等于可视末行下标**（否则两种实现结果相同，用例无意义）；不满足即视为失败而非静默跳过。
5. 拖拽后 `rules` 被整体替换，`pageTable` 的 `tableData` 侦听器会清空列搜索条件并恢复全量展示。

#### 测试数据

- 受控集合 3 条，`cond` 刻意构造为：第 1 条 `req_path_in("/v1/chat/completions", false)`、第 2 条 `default_t()`、第 3 条 `req_path_in("/v1/chat/completions", false) && req_method_in("POST")`。
- 排序场景：第 1 条以 `req_path_in` 开头、第 2 条以 `default_t` 开头，按「生效条件」倒序后可视首行来自源下标 2（≠ 0）。
- 筛选场景：第 1 条是第 3 条的前缀子串，故用第 1 条整串搜索只命中第 1、3 行（2/3 行，可视末行的源下标为 2 ≠ 可视末行下标 1）。

#### 补充说明

- AI 上下文压缩规则的列均为 `sortable: 'custom'` 且未设置 `customSort`，故 `pageTable.sortChange` 走**本地排序**分支，`showSrcIndex` 与行同步重排，源下标映射完整。
- 表格无固定列，`.show-iView-Table .ivu-table-body tbody tr` 与 `getRuleCondsInOrder` 读到的行集合一致。

### AX-DR-03（列搜索态）前置瞬态的定性与修复

失败栈指向 `openRulesInEditMode` 内的 `expectAiContextPageReady`（`.ai-context` 不存在）。排查结论：

- mock 的匹配式**不过宽**：`**/open-api/v1/ai-context-rules` 只命中数据接口；已验证它**不**命中前端路由文档请求 `/ai-context-rules`、也不命中 `/ai-context-settings`（用 Playwright 同语义的 glob→RegExp 复算比对）；

- **找到一处确定性隐患**：共享的 `gotoAiContextPageAndWaitForRules` 内部用宽谓词等待（`url 含 /ai-context-rules` + GET + 200），而前端路由与数据接口共用这段字符串，**SPA 文档请求本身就会满足它**，于是等待可能在 Vue 挂载前返回，之后仅靠固定 `1500ms` 沉降 + 默认 `10s` 断言超时兜底；首次编译 / 热重编译（当时有并发工作流在改产品源码，dev server 会重编译）就会撞上空白窗口。
- **修复（只改测试侧前置写法）**：本 spec 统一改走 `openRulesWithMock`：①注册**只认数据接口**（`resourceType() !== 'document'`）的响应等待 → ②再导航 → ③断言 `.ai-context` 根可见（`expectAiContextPageMounted`，30s 挂载余量）。共享助手与其它 spec 未改动，避免把「超时降级重跑」这类隐式重试扩散到既有用例。

**状态**：`已通过`（2026-10-16 时点为「🚧 阻塞」——已实证为**产品缺陷**；用例预期正确，断言**原样保留**（未加轮询 / 重试 / 放宽）；产品修复后 2026-10-17 复跑转绿，该阻塞已解除，见下条）

**影响用例**：AX-DR-01 第 5 条、AX-DR-05 第 4 条（同一处断言：退出编辑模式后行 `draggable` 应被回收）
**实证时间**：2026-10-16（同构模块 ai-cache 真实浏览器探针 + ai-context 自动化失败串一致）

### 现象

退出编辑模式后，规则表格的数据行仍带 `draggable="true"`，与视图模式应有的「不可拖拽」不符：

1. 编辑模式：行 `draggable="true"`（符合预期）；
2. 退出编辑模式：无改动，确认框确实未弹，页面确已回到视图模式（「进入编辑模式」按钮可见、`.drag-tip` 已不渲染）；
3. 但数据行仍为 `draggable="true"`，且 `@dragstart/@drop/@dragover` 事件绑定同样残留 —— 视图模式下**仍能拖行，并会静默重排本地 `rules` 数组**。

自动化报错原文（断言未改动）：

```text
Expected: null
Received: "true"
第 1 行 draggable 属性不符
```

### 探针实测时间轴

在**同构模块 AI 缓存**（`src/modules/AICache/index.vue`，与本模块共用 `pageTable` + iView Table）上做真实浏览器探针，ai-context 侧自动化报错串与之完全一致：

- 进入编辑模式 → 读取数据行 `draggable` = `["true","true","true"]`；
- 点击「退出编辑模式」→ 无改动，未弹确认框；
- 退出后按 **200ms / 800ms / 2000ms / 5000ms** 多次读取 → 均为 `["true","true","true"]`；
- 同一时刻页面已确实处于视图模式（「进入编辑模式」按钮可见）。

结论：**不是时序问题**，不存在「稍后会自动回收」的时间窗口；该属性在行元素存活期间**永不回收**。

### 根因方向与源码依据

- `src/components/table/pageTable.vue:54`：`:draggable="draggable"` 透传给 iView Table；
- `node_modules/iview/src/components/table/table.vue`：向 `table-head` / `table-body` / 固定列 body 逐层下传；`table-body.vue:9` 再传给 `table-tr`；
- 缺陷落点 `node_modules/iview/src/components/table/table-tr.vue:2`：

```html
<tr :class="rowClasses(row._index)" :draggable="draggable" @dragstart="onDrag($event,row._index)"
    @drop="onDrop($event,row._index)" @dragover="allowDrop($event)" v-if="draggable"><slot></slot></tr>
<tr :class="rowClasses(row._index)" v-else><slot></slot></tr>
```

两个分支都是 `<tr>` 且**没有 `key`**：`draggable` 由 `true` 变 `false` 时 Vue 2 认为「同一元素」只做原地 patch，而 `draggable` 与三个拖拽事件只声明在 `v-if` 分支上，`v-else` 分支不声明 → 属性与事件监听残留，元素不会被替换重建 ⇒ 表现为 `draggable="true"` 永久存在。

### 影响面

- **模块**：三个同构规则模块（AI 缓存 / AI 上下文压缩 / 流量镜像）均受影响；
- **角色**：只读系统管理员视角**不受影响** —— 只读态 `rulesMode` 恒为 `view`，从未渲染过 `draggable=true` 的行；
- **数据面**：视图模式（含刚退出编辑模式的会话）下拖行会改变本地 `rules` 顺序。此时「提交并生效」按钮不渲染（`originalRows === null` → `isRulesDirty` 恒 false），故不会立刻推送；但这批被重排的顺序会成为**下一次**进入编辑模式时 `originalRows` 的快照，用户随后的「提交并生效」会把这次非预期重排一并写入后端。

### 恢复条件

产品侧任选其一修复（三模块同构，需一并处理）：

1. `table-tr.vue` 的两个分支加 `key`，或合并为单个 `<tr>` 并按需条件绑定 `draggable` / 拖拽事件，使 `draggable` 变化时属性与事件被正确清理；
2. `pageTable.vue` 侧在 `draggable` 变化时强制重建表格（如给 Table 加随 `draggable` 变化的 `:key`）；
3. 业务模块退出编辑模式时让表格数据整体重建（当前 `performExitRulesEditMode` 只替换数组、不重建表格）。

修复后处置：重跑 `tests/ai-context/test_07_ai_context_drag_leave.spec.js`，AX-DR-01 / AX-DR-05 应从「阻塞」转「已通过」，并同步回写本文件与 `00-索引与映射.md` 的状态；其余 4 条预期不受该缺陷影响。
