## 4. 只读管理员视角（写操作隐藏）

> 变更依据：`design-docs/modifications/2026-10-12-readonly-admin/ui-code-changes.md`（已 Review 通过）。
> 后端以 `role` 枚举取代 `is_admin`（`system_admin` / `system_admin_readonly`）；只读视角（`role === 'system_admin_readonly'`）**全站隐藏所有写操作按钮**，仅保留只读入口（详情 / 查看 / 查询）。前端实现为全局指令 `v-has`：只读登录态下给挂载元素加 `.v-has-hidden { display:none !important; }`。
> 批量任务页（`pages/batches.html`，源码 `src/modules/BatchTasks/index.vue`）只读视角**仅保留「详情」**、隐藏「取消」等写操作；详情抽屉（`components/BatchView.vue`）本身为纯只读，无写操作入口。

> **数据策略（本节 3 条用例统一）**：**复用环境已有数据，不造数、不清理**。批量任务只能由数据面经 provider 透传产生（控制面无创建接口），本机数据由 `scripts/seed-batch-task-data.cjs`（`npm run seed:batch:execute`，25 条任务 / 10 条文件，覆盖 9 种状态）灌入，属模块既有环境数据（同 `01-列表页.md` / `03-取消.md` 的前置）；只读断言只读不写，因此 spec 无需 `afterAll` 清理。自动化 `tests/batch-tasks/test_04_batch_task_readonly.spec.js` 的 `beforeAll` 用**独立 admin context 只读检索**列表，解析出「非终态 / 终态」各一个可用状态值（供 UI「任务状态」筛选定位样本行）与首行 `batch_id`（BT-RO-03 目标任务及其 `batch_files` 就绪性）。环境无数据时对应用例显式跳过并提示造数命令，不静默通过。

### BT-RO-01：只读视角列表工具栏无写入口且只读控件保留

**功能模块**: 批量任务列表
**优先级**: P0
**用例编号**: BT-RO-01
**OpenAPI**: `GET /batches`

#### 前置条件

1. 以**只读系统管理员**登录（`role=system_admin_readonly`，原型 `viewer` 账号语义）。
2. 「批量任务」菜单可达并进入列表页。

#### 测试步骤

1. 进入「批量任务」列表页。
2. 观察筛选栏区域的按钮区（任务状态 / 服务商 / API Key ID / 创建时间 / 查询 / 重置）。
3. 逐项核对工具栏是否存在任何写操作入口。

#### 预期结果

1. 筛选栏仅保留只读控件（状态下拉、服务商下拉、API Key ID 输入、创建时间起止、查询、重置），**不含任何创建 / 新增 / 编辑写入口**（一期本就不含创建）。
2. 页面筛选与查询交互正常（可正常发起 `GET /batches` 检索）。
3. 切换为系统管理员（`role=system_admin`）登录时，工具栏展示一致（批量任务工具栏本身无写按钮，作为对照说明）。

#### 测试数据

- 只读账号：`role=system_admin_readonly`（`viewer` / `viewer123`，已在联调环境存在）
- 管理员账号：`role=system_admin`（`conf.json` 默认账号）
- 批量任务：**复用环境已有数据**（`npm run seed:batch:execute` 灌入的集合），列表非空即可；spec 不造数、不清理

#### 补充说明

- 隐藏实现：写按钮挂全局指令 `v-has`，只读视角加 `.v-has-hidden`；前端隐藏外，后端对写端点（`POST /batches/{batch_id}/cancel`）做 403 兜底。
- 工具栏本身无写按钮：源码筛选栏（`src/modules/BatchTasks/index.vue:18-84`）只有「查询」「重置」两个 `Button`，一期无创建 / 编辑入口，故本用例的断言形式是「只读控件齐全 + 按钮集合恰为『查询』『重置』」，写入口按候选文案（新增 / 创建 / 编辑 / 删除 / 提交 / 批量取消）逐项断言不存在。
- **文档与实现的措辞差异**：预期 1 写「服务商下拉」，实现为 `Input` 输入框（`index.vue:37-41`，占位符「按服务商过滤」），自动化按输入框断言。

### BT-RO-02：只读视角列表操作列「取消」隐藏「详情」保留

**功能模块**: 批量任务列表
**优先级**: P0
**用例编号**: BT-RO-02
**OpenAPI**: `GET /batches`

#### 前置条件

1. 以**只读系统管理员**登录，列表中存在至少一条批量任务记录（含非终态与终态各 ≥ 1 条更佳）。

#### 测试步骤

1. 进入「批量任务」列表页。
2. 观察列表行尾「操作」列的按钮。
3. 点击该行的「详情」。

#### 预期结果

1. 操作列**隐藏**「取消」按钮（对应源码操作列取消按钮挂 `directives: [{ name: 'has' }]`）。
2. 操作列**保留**「详情」按钮（不隐藏），点击可打开只读详情抽屉。
3. 管理员视角（`role=system_admin`）下操作列「详情」「取消」均显示：非终态「取消」可用、终态「取消」置灰（`title="终态任务不可取消"`）。（对照组）

#### 测试数据

- 只读账号：`role=system_admin_readonly`
- 存在 1 条以上批量任务记录：**复用环境已有数据**，且需「非终态」「终态」各 ≥ 1 条（预期 3 对照组要同时覆盖两种态的「取消」可用性）。自动化在 `beforeAll` 从环境数据解析出首个非终态、首个终态样本的**状态值**，用例按「任务状态」筛选把样本行收敛到列表首页后再断言
- 样本状态示例：非终态 `queued`、终态 `completed`（实际取值以环境数据为准，不硬编码）

#### 补充说明

- 依据变更记录 §3.4：`pages/batches.html` 只读视角保留「详情」，隐藏「取消」等写操作。
- 断言方式：行内「取消」挂 `v-has`（`index.vue:365` 终态 / `:381` 非终态），只读视角**仍在 DOM 中**且带 `.v-has-hidden`，因此用 `expectVHasHidden`（而非「不存在」）；「详情」不挂任何指令，只读视角可见。
- **2026-10-16 首轮串行验证：预期 1 失败，失败点在「只读态列表重渲染」**——只读视角**首次进页**时 `.v-has-hidden` 正常（20 个，与全站巡检 `UM-53`、`test_11_readonly_sweep.spec.js` 的 `/batches` 用例一致），但**按「任务状态」筛选触发列表重渲染后**，命中行（`batch-seed-02`，非终态变体）的「取消」变成 `class="ivu-btn ivu-btn-error ivu-btn-small"`（无 `.v-has-hidden`、可见），断言失败。
  - **排除「被换回管理员态」分支**（证据）：① 后端 `ai-gateway-runtime/log/access.log` 在失败窗口（16:51:07–16:51:22）**无任何 401**（全窗口仅一次 402，来自 cluster 只读探针），即产品侧 `src/utils/request.js:113-115` 的 `removeUserData()`（401 路径）未触发；② 窗口内**无第二次登录**（`POST /auth/session-keys` 仅 16:51:01 / 16:51:06 / 16:51:25 三次，属三个用例各自的只读登录）；③ `expectStillReadonly`（localStorage）通过，且失败窗口内 viewer 的两次 `/batches` 请求均 200。
  - **判定**：属「筛选（列表重渲染）后 class 丢失」分支 → 产品 `v-has` 在列表重渲染时的挂载机制问题（**待产品侧确认**；`v-has` 指令只有 `inserted`/`update`，见 `src/utils/directive.js:46-49`，而 Vue 的 directive `inserted` 是经 `mergeVNodeHook` 挂到 vnode insert 钩子上的**一次性**回调，见 `vue/src/core/vdom/helpers/merge-hook.ts:20-25` + `vue/src/core/vdom/modules/directives.ts:57-66`；iView 表格 `components/table/expand.js` 是 functional 组件包装各列 `render`，`table-body.vue` 行 key = 行下标，筛选后「行对象换位 + 组件复用」的路径与之相关——**具体触发点待下一轮诊断确认**）。
  - **复现步骤**：只读（`viewer`）登录 → 直连 `/batches`（此时行内「取消」均带 `.v-has-hidden`，页面级 count=20）→「任务状态」选择任一非终态状态 → 点「查询」→ 断言命中行「取消」的 class。
  - **证据**：Playwright 失败归档 `test-results/tests-batch-tasks-test_04_-ea077-只读抽屉；管理员非终态「取消」可用、终态置灰（对照组）/error-context.md`（含失败 locator、实际 class、24 次重试记录）、[report/test-report-20261016-170124.md](../../../report/test-report-20261016-170124.md)、后端 `ai-gateway-runtime/log/access.log`（16:51 窗口）、[测试问题复盘](../测试问题复盘.md) **BUG-BT-02**。
  - **处置**：**保留断言**（不迁就实现改写预期），生命周期按 `阻塞` 记录；自动化已加诊断步骤（进页后 / 筛选后各断言一次页面级 `.v-has-hidden` 数量，并输出 `store.isReadonly()` 与命中按钮 class），供下一轮串行验证定位到具体交互。筛选交互已由「直写 `vm.filter.status`」改为**真实 UI 下拉 + 查询**（同 BT-L-02 路径），以排除测试态直写这一变量。
  - **✅ 结案（2026-10-17）**：产品缺陷 **BUG-BT-02 当日修复** —— `v-has` 指令补**同名属性兜底**（`src/utils/directive.js` 新增 `HIDDEN_ATTR='v-has-hidden'`，加/删类的同时 `setAttribute` / `removeAttribute`），`global.less` 隐藏选择器扩为 `.v-has-hidden, [v-has-hidden]`；定性的根因是 **`v-has` 用命令式 `classList.add`，而 iView Button 的 class 有响应式属主，按钮 props 变化触发组件自身重渲染时 Vue class 模块整串重写 class 属性、把命令式类抹掉**（上方「待产品侧确认 / 具体触发点待下一轮诊断确认」至此已有定论，见 `ai-gateway-web/design-docs/modifications/2026-10-17-ui-defect-fixes/ui-code-changes.md` §4.1）。修复后该行 `class` 仍可能被抹掉（原现象未被掩盖），但 `[v-has-hidden]` 属性在、命中 `display:none`，不再是可见写入口。测试侧复跑本 spec **BT-RO-01/02/03 3/3 全绿**（断言未改、口径为「可见性 + 类或属性至少一种」，见 `utils/readonly.js:230-241`），证据 [report/test-report-20261017-130924.md](../../../report/test-report-20261017-130924.md)、[report/test-report-20261017-134114.md](../../../report/test-report-20261017-134114.md)；本用例生命周期由 `阻塞` 回写 `已通过`。上方 2026-10-16 的失败、排除分支与诊断记录按原文保留，作为过程存档。

### BT-RO-03：只读视角详情抽屉纯只读无写入口

**功能模块**: 批量任务详情
**优先级**: P0
**用例编号**: BT-RO-03
**OpenAPI**: `GET /batches/{batch_id}`

#### 前置条件

1. 以**只读系统管理员**登录，列表中已存在至少一条批量任务记录。

#### 测试步骤

1. 点击某条批量任务的「详情」，打开右侧抽屉（标题「批量任务详情」）。
2. 观察抽屉内 5 个 panel 卡片与「批量文件」表格区域。
3. 核对抽屉内是否存在任何写操作按钮（取消 / 编辑 / 提交等）。

#### 预期结果

1. 详情抽屉为**纯只读**，抽屉内**不含任何写操作按钮**（源码 `components/BatchView.vue` 无写入口，无 `v-has` 写按钮）。
2. 5 个 panel 卡片（基本信息 / 状态与计数 / 用量与记账 / 文件与时间 / 批量文件）与 `batch_files` 表格正常只读展示。
3. 管理员视角打开同一抽屉展示内容一致（详情抽屉不因角色变化而增减内容）。（对照组）

#### 测试数据

- 只读账号：`role=system_admin_readonly`
- 目标任务：**复用环境已有数据**（`beforeAll` 取列表首行 `batch_id`，管理员 / 只读两次打开同一任务，保证预期 3 的「同一抽屉」可比），不造数、不清理
- `batch_files` 就绪性：`beforeAll` 顺带以 admin context 读一次详情接口，记录该任务是否返回扁平 `Data.batch_files`（供预期 2 的数据守卫判定，见补充说明）

#### 补充说明

- 详情抽屉本身无写操作，只读视角无需额外隐藏；本用例用于确认「只读入口保留 + 无写按钮残留」。
- **预期 2 的 `batch_files` 表格子断言受 BUG-BT-01 影响（已实测确认）**：当前实现 `GET /batches/{batch_id}` 返回 `Data = {task, files}`（2026-10-16 16:51 轮次实测，见 `ai-gateway-runtime/log/access.log`），与 `batches.md` 契约（`Data` 即任务对象、内含 `batch_files`）不符，`BatchView.vue` 取不到数据 → 表格 `v-if="batchFiles.length"` 恒不渲染、全部字段渲染 `-`。此子断言沿用 `02-详情页.md` 中 BT-D-03 的**数据就绪守卫**（就绪才断言表头 / 行数，否则只断言「批量文件」区域存在），**不迁就实现改写预期**；接口修复后守卫分支自动生效 → 该子断言当前状态为 **`阻塞`（BUG-BT-01）**。证据见 [测试问题复盘](../测试问题复盘.md) BUG-BT-01。**2026-10-17 结论**：BUG-BT-01 已由 `ai-gateway-api` commit `b568dce` 修复，本子断言随之从「数据就绪守卫降级」转为**真数据断言**并通过（实测真机渲染 2 条文件元数据），本 spec **3/3 全绿**（[report/test-report-20261017-130924.md](../../../report/test-report-20261017-130924.md)、[report/test-report-20261017-134114.md](../../../report/test-report-20261017-134114.md)）；生命周期回写 `已通过`。
- **2026-10-16 首轮串行验证：本用例失败于用例自身缺陷（已修）**——「批量文件」区域步骤把 `utils.batchFilesEmpty(page)`（async 函数，返回 Locator）的 **Promise** 直接传给了 `expectReadonlyVisible`，报 `toBeVisible can be only used with Locator object`；已改为先 `await` 再断言。该失败与 BUG-BT-01 的守卫分支无关（是断言写法问题），修复后守卫分支的「空占位可见」断言应通过。
