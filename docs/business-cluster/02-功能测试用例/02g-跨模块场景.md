### BC-J-01：从零搭建可路由链路（Provider → Cluster → Route → 审计 → 反序清理）

**功能模块**: AI业务集群（跨 Providers / 路由管理 / 操作日志）  
**优先级**: P0  
**用例编号**: BC-J-01  
**设计依据**: [01-测试场景概览](../01-测试场景概览.md)「配置顺序 ①②③」；entity-management `EM-J-01` 全 UI 流程先例  
**自动化**: `tests/cluster/test_14_business_cluster_full_journey.spec.js`

#### 前置条件

- admin 登录；Providers / Clusters / Route / 操作日志四个模块入口可达
- 全局路由规则可进入编辑模式（用例内自动停用-恢复，afterEach 快照还原）

#### 测试步骤

1. Providers UI 创建服务商：IP 实例（127.0.0.1:80 权重 100）、协议 openai、批量添加模型、Key 一行
2. 操作日志 UI：按资源名搜索该服务商，核对审计记录
3. Clusters UI 走完 5 步向导创建集群：引用上述服务商、选该模型、服务商 Key 权重 100
4. 操作日志 UI：按资源名搜索该集群，核对审计记录
5. Route UI：默认路由表进入编辑 → 新增规则 `default_t()` 引用该集群（模型 + 权重 100）→ 本地保存 → 提交并生效
6. Clusters UI：删除该集群 → 被引用拦截
7. Route UI：删除该规则并提交生效 → Clusters UI：删除集群成功
8. Providers UI：删除服务商成功
9. 操作日志 UI：按资源名搜索该集群，核对删除记录

#### 预期结果

1. 步骤 1/3/8 各步 UI 操作成功且列表可见对应对象（服务商 → 集群 → 服务商删除后不可见）
2. 操作日志：服务商 `create` 记录、集群 `create` 记录、集群 `delete` 记录均可按资源名检索到（审计完整性）
3. 步骤 5 提交后规则出现在路由表且提交生效无报错（引用链建立）
4. 步骤 6 删除失败 toast 后端错误消息（含引用规则名，引用约束生效；2026-11-04 起前端不再弹引用信息窗，校验由后端承担）
5. 步骤 7 删除规则后集群删除成功（引用解除与清理顺序正确）
6. 全程无页面报错、无控制台告警

#### 补充说明

- 本用例同时覆盖「跨模块导航 / 引用链建立与解除 / 审计完整性 / 清理顺序」四个维度，替代零散的跨模块单点断言（如 RM-BC-14 仅覆盖删除拦截）
- 造数即本用例自身；afterEach 兜底清理顺序为「路由规则（快照还原）→ 集群 → 服务商」

### BC-J-02：换服务商演练（编辑态状态机）

**功能模块**: AI业务集群  
**优先级**: P0  
**用例编号**: BC-J-02  
**设计依据**: `ai-gateway-web` `GatewayConfig.syncFormWithProvider`（切换 provider 的模型过滤 / Keys 清空语义）  
**自动化**: `tests/cluster/test_13_business_cluster_provider_switch_journey.spec.js`

#### 前置条件

- 存量集群引用 Provider A：2 个转发模型（A1/A2）+ 2 个 Keys（权重 70/30）
- Provider B 已存在：1 个模型（B1）+ 1 个 Key（KB1）

#### 测试步骤

1. UI 打开该集群编辑向导，进入第 4 步「大模型配置」
2. 读取转发模型与 Keys 回显（应为 Provider A 的 A1/A2 与两个 Key）
3. 将「所属服务商」切换为 Provider B
4. 观察转发模型与 Keys 行的变化
5. 重新选择 B1 模型、选择 Key KB1 并将权重改为 100，进入复查并提交
6. `GET /clusters/{name}` 读回比对

#### 预期结果

1. 切换前回显为 Provider A 的模型与 Keys（步骤 2 通过）
2. 切换后**转发模型被过滤为空**（A1/A2 不在 B 的模型列表）
3. 切换后 **Keys 行保留但名称清空（下拉回落 placeholder）、权重保留**（70/30）；空名称行不参与权重和校验
4. 重新配置后可进入复查；`PATCH` 提交体为 `provider=B`、`models=[B1]`、`keys=[{name:KB1, weight:100}]`，旧模型/旧 Key 无残留
5. `GET` 读回与提交一致

#### 补充说明

- 编辑态与创建态是两套代码路径（`applyLlmConfig` + `loadProviderDetail` vs `fillModelStep`），本用例是编辑态状态机的唯一覆盖
- 若产品后续改为「切换 provider 需二次确认/整体清空」，本用例需按新语义修订（现有实现为静默过滤+清空）

### BC-J-04：完整配置面（Provider → Cluster → Route → AI 缓存 → 流量镜像，反序拆除）

**功能模块**: AI业务集群（跨 Providers / 路由管理 / AI 缓存规则 / 流量镜像规则）  
**优先级**: P0  
**用例编号**: BC-J-04  
**设计依据**: 覆盖缺口清单 #41（功能增强层从未纳入主链路）；与 BC-J-01 差异见下  
**自动化**: `tests/cluster/test_18_business_cluster_enhanced_journey.spec.js`（2026-10-30 定向 1/1 通过，2.1m）

#### 前置条件

- admin 登录；五个模块入口可达
- 缓存/镜像集合与全局路由规则可快照还原（afterEach 兜底）

#### 测试步骤

1. Providers UI 创建服务商（IP 实例 + openai + 批量模型 + Key）
2. Clusters UI 走完 5 步向导创建集群（引用该服务商 + 模型 + Key 权重 100）
3. Route UI 新建规则 `default_t()` 引用该集群（模型 + 权重 100），本地保存并提交生效
4. AI 缓存 UI 进入编辑模式，新增集合级规则（`default_t()`），本地保存并提交并生效
5. 流量镜像 UI 进入编辑模式，新增集合级规则（`default_t()`），本地保存并提交并生效
6. 反序拆除：删缓存规则（提交并生效）→ 删镜像规则（提交并生效）→ 删路由规则（提交生效）→ 删集群 → 删服务商

#### 预期结果

1. 五层配置在同一 UI 会话中全部走通，各自列表可见对应产物
2. 反序拆除每步成功，列表行消失；集群删除不受缓存/镜像规则阻塞（两者 cond 无集群原语、不引用集群对象——已核实 ExpressionConfig.js）
3. 全程无页面报错；afterEach 快照还原缓存/镜像集合与全局路由规则

#### 补充说明

- 与 BC-J-01 的差异：BC-J-01 覆盖主链 + 审计核对 + 引用约束；本用例把功能增强层纳入配置面，验证五层互不阻塞、可按依赖反序拆除
- 覆盖缺口清单 #42（EPP 调度闭环）为下一跨模块场景（BC-J-05，待排期）
