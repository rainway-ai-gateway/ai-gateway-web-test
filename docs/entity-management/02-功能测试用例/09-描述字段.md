## 8. Entity 描述（2026-09-22）

> 变更背景：
>
> 1. **Entity 新增可选字段 `description`**：长度 0–255 **字节**（按 UTF-8 字节计）；不能包含控制字符；**非必填**（留空允许提交）。
> 2. **创建 / 编辑表单**：「描述」**不加必填星号**；**不展示提示小字**；placeholder 为「请输入Entity描述」（不体现「选填」）。
> 3. **列表**：新增「描述」列（位置：名称 → 描述 → 类型）；空值展示 `-`；支持搜索（placeholder「请输入描述查询」）与排序。
> 4. **详情**：基本信息区新增「描述」行（顺序：名称 → 描述 → 类型）；空值展示 `-`。
> 5. **提交语义**：编辑走 `PATCH /entities/{id}` —— 省略 `description` 保留原值，显式传空字符串 `""` 清空。
>
> 接口依据：`entities.md` §2.1 字段表 `description`、§2.2 创建 body、§3.2 响应体、§4.1 PUT（全量，省略即清空）、§4.2 PATCH（增量，省略保留 / `""` 清空）；DDL `db_ddl_sqlite.sql` `entities.description TEXT NOT NULL DEFAULT ''`。  
> UI 依据：`modifications/2026-09-22-entity-description-and-protocol-paths/ui-code-changes.md`；原型 `prototype-design/assets/js/entity-upsert.js`、`prototype-design/pages/entity.html`。
>
> **长度口径变更（2026-10-22）**：`description` 由「0-255 字符」改为「0-255 字节（按 UTF-8 字节计）」，控制字符约束不变。UI 保留模板 `maxlength=255`（按**字符**截断）并叠加字节校验，多字节字符在字符数未超限、字节数超限时由校验拦截并在字段下方报错。**该口径落在既有用例 EM-DESC-03，本文件未新增用例。**  
> 变更依据：`../../../../ai-gateway-web/design-docs/modifications/2026-10-22-desc-bytes-and-cache-cond-unique/ui-code-changes.md` §2 / §4；接口 `entities.md` §1/§2.1/§2.2/§4.1/§4.2。

### EM-DESC-03：创建 Entity-描述字节长度与控制字符校验

**功能模块**: Entity 描述  
**优先级**: P1  
**用例编号**: EM-DESC-03  
**设计依据**: 原型 `entity-upsert.js` `validateEntityDescription`；`ui-code-changes.md` §2.1 / §2.2；2026-10-22 字节口径变更（`EntityUpsert.vue:602-618` 校验改 `utf8ByteLength` 0-255，模板保留 `maxlength=255`）；i18n `entity.descriptionLengthError` / `entity.descriptionControlCharsError`  
**OpenAPI**: `entities.md` §2.1 / §2.2（POST）、§4.2（PATCH）「非必填；若传入，长度 0-255 字节（按 UTF-8 字节计）；不能包含控制字符」

#### 前置条件

- 已登录系统并进入 Entity 组织管理页面，已存在至少一个 Entity 类型
- 打开创建 Entity 抽屉（步骤 8 使用步骤 2 创建成功的 Entity 的编辑抽屉）
- 后端已按字节口径校验：255 字节 ASCII 通过；200 个汉字（200 字符 / 600 字节）返回 `422 Param Illegal: description length must be <= 255`

#### 测试步骤

1. 名称填 `desc_bytes_{时间戳}`、选择类型，描述输入 255 个 ASCII 字符（`a`×255 = 255 字节），提交
2. 重新打开创建抽屉，名称填 `desc_bytes_zh_{时间戳}`、选择类型，描述输入 85 个汉字「描」×85（85 字符 / **255 字节**），提交
3. 重新打开创建抽屉，描述输入 86 个汉字「描」×86（86 字符 / **258 字节**），提交
4. 重新打开创建抽屉，描述输入 200 个汉字「描」×200（200 字符 / 600 字节），提交
5. 描述输入 256 个 ASCII 字符，观察输入框截断行为
6. 描述中粘贴含控制字符的内容（如换行 `\n`、制表符 `\t`），提交
7. 描述留空，提交
8. 打开步骤 2 创建成功的 Entity 编辑抽屉，将描述改为 200 个汉字后提交
9. 捕获步骤 3、4、6、8 点击「确定」后的网络请求

#### 预期结果

1. 255 字节（ASCII）通过校验，`POST /entities` 返回 200；列表「描述」列展示 255 个字符原文
2. 85 汉字 = 255 字节，处于边界值合法侧，通过校验并可提交成功（中文不被误拦截）
3. 86 汉字 = 258 字节，超出上限，字段下方报错「Entity描述不能超过255字节（按 UTF-8 字节计）」；**不发出** `POST /entities` 请求
4. 200 汉字（600 字节）同样被拦截，文案同步骤 3；字符数 200 未触及 `maxlength=255`，但字节数超限仍拦截
5. 输入框 `maxlength=255` 按**字符**截断，无法录入第 256 个字符；字符截断与字节校验同时生效（多字节场景见步骤 3、4）
6. 含控制字符时校验拦截，字段下方提示「Entity描述不能包含控制字符」，不发请求
7. 描述留空通过校验（**非必填**），可正常提交成功
8. 编辑（PATCH）与创建同口径：200 汉字被拦截并提示同一文案，原描述保持不变
9. 步骤 3、4、6、8 均无成功请求；如绕过 UI 直连接口提交 200 汉字，后端返回 `422 Param Illegal: description length must be <= 255`（UI 与后端判定一致，不出现 UI 放行、后端 422 的错位）

#### 测试数据

- Entity 名称：`desc_bytes_{时间戳}`（步骤 1）、`desc_bytes_zh_{时间戳}`（步骤 2）、`desc_empty_{时间戳}`（步骤 7）；提交失败的行不落库
- 描述样本：ASCII `a`×255（255 字节）/ 汉字「描」×85（255 字节）/「描」×86（258 字节）/「描」×200（600 字节）/ 含 `\n`、`\t` 的控制字符串
- 清理：删除步骤 1、2、7 创建成功的 Entity（无下级、无挂载 API-Key）
