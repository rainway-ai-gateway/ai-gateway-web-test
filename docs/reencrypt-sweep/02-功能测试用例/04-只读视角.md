## 4. 只读管理员视角（写操作隐藏）

> **归属场景**: 场景五（只读管理员视角（写操作隐藏））
> 变更依据：`design-docs/modifications/2026-10-12-readonly-admin/ui-code-changes.md`（已 Review 通过）。
> 后端以 `role` 枚举取代 `is_admin`（`system_admin` / `system_admin_readonly`）；只读视角（`role === 'system_admin_readonly'`）**全站隐藏所有写操作按钮**，仅保留只读入口（列表 / 查看 / 查询）。前端实现为全局指令 `v-has`：只读登录态下给挂载元素加 `.v-has-hidden { display:none !important; }`。
> 密钥收敛页（`src/modules/Security/index.vue`）只读视角**隐藏触发区「触发任务」按钮**（该按钮即 `POST /security/reencrypt-sweeps` 触发入口），仅保留历史列表与任务详情的只读查看。

### RS-RO-01：只读视角触发区「触发任务」按钮隐藏

**功能模块**: 触发
**优先级**: P0
**用例编号**: RS-RO-01
**OpenAPI**: `POST /open-api/v1/security/reencrypt-sweeps`

#### 前置条件

1. 以**只读系统管理员**登录（`role=system_admin_readonly`）。
2. 具备 `FeatureSecurity`（scope=System）`read` 权限，「密钥收敛」菜单可达并进入页面。

#### 测试步骤

1. 进入「系统安全 → 密钥收敛」页面。
2. 观察触发区（`security.triggerCardTitle` 「触发收敛任务」卡片）内的按钮。
3. 核对是否存在「触发任务」（`security.trigger`）写入口。

#### 预期结果

1. 触发区**不显示**「触发任务」按钮（对应源码 `src/modules/Security/index.vue` 该 `Button` 挂全局指令 `v-has`，只读视角加 `.v-has-hidden`）。
2. 页面无任何可触发 `POST /security/reencrypt-sweeps` 的入口。
3. 切换为系统管理员（`role=system_admin`）登录时，「触发任务」按钮正常显示（对照组）。

#### 测试数据

- 只读账号：`viewer` / `viewer123`（`role=system_admin_readonly`，联调环境已存在，见 `utils/readonly.js`）
- 管理员账号：`role=system_admin`（`conf.json` 凭证 / `auth.json` 会话）
- **数据策略：无需造数**。本用例只断言触发区按钮可见性，历史列表与运行中卡片有无数据均不影响断言；只读断言只读不写。

#### 补充说明

- 隐藏实现：触发按钮挂全局指令 `v-has`，只读视角加 `.v-has-hidden`；前端隐藏外，后端对写端点做 403 兜底。
- 源码依据：`src/modules/Security/index.vue:61-67`「触发任务」`Button` 上的 `v-has` 是本页**唯一**挂 `v-has` 的元素；触发区的「变换方向 / 扫描范围 / 预演模式」表单控件未挂 `v-has`，只读视角仍渲染（属产品设计，不在本用例断言范围内）。
- 自动化补充：本用例在**真实环境（不做任何网络 mock）**直连进入页面，并断言只读账号的 `GET /security/reencrypt-sweeps` 返回 **200**，证明只读角色的读取能力未被写入口收敛影响；RS-RO-02/03 的列表 / 详情样本才用 fixture（原因见该两条的「测试数据」）。
- **自动化定位约定（2026-10-16 首轮教训）**：`v-has` 用 `display: none` 隐藏写元素，而 Playwright 的 `getByRole` 基于无障碍树、**看不见** `display:none` 元素 —— 只读态用 `getByRole('button', { name: '触发任务' })` 会得到 count 0，断言「仍在 DOM 中」必然误报（首轮 RS-RO-01 即因此失败）。故：只读态针对 `v-has` 元素一律用 **CSS + 文本** 定位（`pages/security/ReencryptSweepPage.js` 的 `triggerSubmitButton` / `readonly.buttonByText`），「无写入口」计数断言也用 CSS 版 locator（`triggerCardActionButtons` 等，否则隐藏元素对 role 定位隐身会导致假通过）；只有**管理员对照组**（元素可见）才用 `getByRole` 的 `triggerButton(page)`。

### RS-RO-02：只读视角历史列表与筛选只读保留

**功能模块**: 历史列表与筛选
**优先级**: P0
**用例编号**: RS-RO-02
**OpenAPI**: `GET /open-api/v1/security/reencrypt-sweeps`

#### 前置条件

1. 以**只读系统管理员**登录，历史列表中已存在若干任务记录（服务端持久化）。

#### 测试步骤

1. 进入「系统安全 → 密钥收敛」页面。
2. 观察历史任务列表、筛选栏与分页 / 排序控件。
3. 使用筛选（状态 / 变换方向 / 扫描范围 / 预演 / 时间）与分页、列头排序操作。

#### 预期结果

1. 历史任务列表正常加载并展示 **9 列**（任务ID / 状态 / 变换方向 / 扫描范围 / 预演 / 触发者 / 开始时间 / 耗时 / 操作），只读视角保留查看。
2. 筛选栏 / 查询 / 重置 / 分页 / 列头排序等**只读控件保留可用**，不影响数据查看。
3. 列表操作列仅保留「详情」只读入口，无任何写操作按钮（触发入口仅存在于触发区，已由 RS-RO-01 隐藏）。
4. 列表中运行中任务同样可查看（运行中横幅展示为只读信息，不提供触发 / 取消写入口）。

#### 测试数据

- 只读账号：`viewer` / `viewer123`（`role=system_admin_readonly`）
- 历史任务 ≥ 1 页（含终态与运行中样本）
- **数据策略：不造数、不改共享环境。** 密钥收敛任务是服务端持久化记录且**无删除端点**，触发真实任务等于把共享环境改写成既有事实（无法还原），因此「造数 + 清理」在本模块不可行。自动化改用网络 fixture（`mockReencryptSweepListServer`）构造 25 行（默认 `page_size=20` → 满足「≥ 1 页」），其中含 `running`（运行中横幅）、`decrypt`（变换方向）、`dry_run`（预演）、`api_keys`（扫描范围）四类样本以覆盖各筛选枚举命中；用例结束 `unmockReencryptSweepNetwork` 解除 mock。运行中样本另以 `mockReencryptSweepDetailRunning` 保持 running，避免轮询进入终态触发列表重取（与 RS-D-03 同款）。
- **运行中样本是确定性的、不依赖环境**：`running` 行由 fixture 提供、详情接口被 mock 恒返回 `running`，故「轮询中…」窗口不会一闪而过。2026-10-16 首轮执行已实测该窗口稳定成立（快照见 `report/test-report-20261016-170124.md` 对应 `test-results/…error-context.md`：`当前运行任务 → 任务ID rsp-ro02-running 状态 运行中 轮询中…`）。**环境本身是否存在运行中任务不影响本用例**（首轮该条失败与数据无关，见下）。

#### 补充说明

- 依据变更记录 §3.4：`security.html` 保留列表 / 详情，隐藏「触发任务」。
- 源码依据：历史表格操作列在 `src/modules/Security/index.vue:369-383` 的 render 中**无条件**只渲染「详情」按钮（无 `directives`），故只读视角操作列天然仅剩「详情」；本页写入口只有触发区那一个 `v-has` 元素。
- **2026-10-16 首轮失败定位（非数据问题，已修）**：失败断言是「运行中横幅『轮询中…』应可见」，但报错 locator 链为 `… .locator('.sweep-view').locator('.sweep-view .sv-polling')` —— `pollingIndicator(root)` 自带 `.sweep-view` 前缀，用例误把 `runningSweepView(page)`（本身就是 `.sweep-view`）当 root，拼成 `.sweep-view` 内再找 `.sweep-view`，**永不命中**。已修为 page object 的 `runningBannerPollingIndicator(page)`（root 传卡片，与本模块 RS-P 用例的 `pollingIndicator(card)` 同款）。**该失败不是「环境缺少运行中任务」**：同一次运行的 ARIA 快照里运行中横幅已渲染出「轮询中…」。

#### 阻塞记录：预演模式筛选的「重置」路径（2026-10-16 第 3 轮实测，`阻塞`）

**状态**：`阻塞`。用例「筛选（预演模式）命中后『重置』应恢复全量」的断言按本文件 + RS-L-09 的文档口径**保留、不弱化**；失败根因是**产品缺陷**，与 fixture 行数、采集时机无关。

**现象**（第 3 轮串行：`report/test-report-20261016-181601.md`）

1. 只读视角把「预演模式」筛成「是」→ 命中 1 条 ✓（构造性 fixture 中唯一 `dry_run=true` 行）。
2. 点「重置」→ 前端「预演模式」显示回到「全部」，但列表请求仍带 `dry_run=false`，结果集停在 **24**（= 全量 25 减去那 1 条 `dry_run=true`），分页器「共 24 条」，10s 轮询内稳定复现（`Expected: 25 / Received: 24`）。
3. 前置的「状态 / 变换方向 / 扫描范围」三次重置均正常回到 25 —— 只有 `dry_run` 这一项会出问题。

**根因链（源码级，可直接定位修复点）**

1. `ai-gateway-web/node_modules/iview/src/components/select/select.vue:724`：`value` 变为 `''` 时执行 `this.values = []`（清空选中项）。
2. 同文件 `:730-740`：`values` watcher 中 `vModelValue = this.publicValue`；而无选中项时 `publicValue` 为 **`undefined`**（`:353-357` 的 `(this.values[0] || {}).value` → `({}).value`），`vModelValue !== this.value`（`undefined !== ''`）成立 → 依次 `emit('input', undefined)` 与 `emit('on-change', undefined)` → `v-model` 把 `filter.dry_run` 写成 `undefined`。
3. `ai-gateway-web/src/modules/Security/index.vue:441`：`if (f.dry_run !== '') params.dry_run = f.dry_run === 'true';` —— 其余筛选项用真值判断（`if (f.status)` / `if (f.mode)` / `if (f.scope)`），**只有 `dry_run` 用 `!== ''`**，于是 `undefined` 通过判断并被折算为 `false` → axios 发出 `dry_run=false`（等价于「预演 = 否」），与界面显示的「全部」矛盾。

**离线复算证据**（以 `index.vue:430-447` 的 `buildListParams` 与 `ReencryptSweepPage.mockReencryptSweepListServer` 的服务端模拟逐行复算，非浏览器）

| `filter.dry_run` | 出参 | 请求 query | mock 命中 total |
| --- | --- | --- | --- |
| `'true'`（筛选态） | `dry_run: true` | `…&dry_run=true` | 1 |
| `''`（`EMPTY_FILTER()` 的**意图值**） | 无 `dry_run` | `…`（无筛选） | **25** ↔ 文档口径 |
| `undefined`（iView **实际写入值**） | `dry_run: false` | `…&dry_run=false` | **24** ↔ 第 3 轮实测 |

**为何既有用例没抓住**：RS-L-09「重置筛选与排序」的自动化只预置了 `status` 筛选，从未预置「预演模式」，因此该路径此前未被任何 spec 覆盖（见 `03-列表与筛选.md` RS-L-09 补充说明）。

**恢复条件**：`index.vue` 把 `dry_run` 判定改为真值判断（或 `onReset` 后把 `undefined` 归一化为 `''`）并修复后，本断言（以及 RS-L-09 补预置 `dry_run` 后的断言）应同时转绿。

**影响面**：非只读视角特有 —— 管理员视角同样存在（只在只读视角的逐项筛选 loop 里被触发；一旦触发，**其后每次「重置」都会继续带 `dry_run=false`**，故本文件的时间范围筛选步骤的重置断言也受同一缺陷影响）。

### RS-RO-03：只读视角任务详情抽屉只读查看保留

**功能模块**: 详情
**优先级**: P0
**用例编号**: RS-RO-03
**OpenAPI**: `GET /open-api/v1/security/reencrypt-sweeps/{task_id}`

#### 前置条件

1. 以**只读系统管理员**登录，列表中存在可查看的任务记录。

#### 测试步骤

1. 进入「系统安全 → 密钥收敛」页面。
2. 在历史列表中点击「详情」，打开右侧抽屉。
3. 核对抽屉内容与写入口。

#### 预期结果

1. 详情抽屉正常打开并展示任务字段（task_id / 状态 / 变换方向 / 预演模式 / 扫描范围 / 触发者 / 起止时间 / 耗时 / 按 `scope` 分组的统计块 / 错误）。
2. 详情抽屉为**纯只读**，无任何触发 / 取消 / 编辑等写入口。
3. 运行中任务详情展示「轮询中…」、耗时 `-`、统计占位；dry-run / failed 语义提示正常（与管理员视角一致，仅只读）。

#### 测试数据

- 只读账号：`viewer` / `viewer123`（`role=system_admin_readonly`）
- 终态任务（含 `succeeded` / `failed` / `dry_run` 样本）各 ≥ 1 条
- **数据策略：不造数、不改共享环境。** 同 RS-RO-02：环境真实任务无法删除，且 `failed` / `dry_run` / `running` 样本不保证存在，触发真实任务又会永久改写共享环境。自动化改用 fixture 构造 `succeeded`（`scope=all` 双分组统计）/ `failed`（error 归因）/ `dry_run`（蓝色语义提示）/ `running`（「轮询中…」）各 1 条，逐条打开「详情」抽屉断言；详情本身无写操作，只读断言只读不写。

#### 补充说明

- 密钥收敛详情本身无写操作，只读视角保留完整查看能力（对照 RS-D-01 ~ RS-D-09）。
- 源码依据：详情由 `src/modules/Security/components/SweepView.vue` 渲染（纯展示组件，无按钮 / 无表单控件），抽屉容器 `src/modules/Security/index.vue:212-219` 亦无 footer 写入口。
