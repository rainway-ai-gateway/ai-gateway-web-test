# 跨模块联动

[← 返回索引](./00-索引与映射.md)

## 4. 跨模块联动

> **归属场景**：场景五（Entity/API-Key 与路由表联动）、场景六（全链路配置 @journey）  
> **与功能用例关系**：不替代 §1~§3 单条用例；验证 Entity / API-Key 模块的增删是否在路由表列表同步反映。  
> **后端行为**：创建 Entity / API-Key 时 API 自动初始化 `route_rules`（`enabled=false, rules=[]`）；删除时级联删除对应路由表记录。

---

### 4.1 创建 Entity 后路由表列表新增

**功能模块**：跨模块联动（Entity 组织管理 → 路由表列表）  
**优先级**：P0  
**用例编号**：RT-S-01  
**归属场景**：场景五  
**设计依据**：`ai-gateway-api/endpoints/openapi_v1/entity/create.go`（自动初始化 `route_rules`）

前置条件：

- 已登录系统
- 已存在至少一个 Entity 类型（若无，先 UI 创建类型，见 EM-T-02）
- 路由表列表当前**不包含**待创建 Entity 的 `entity_id` 对应记录

测试步骤：

- 记录进入路由表列表前的表格行数（或按类型 `entity` 筛选后的行数）
- 进入 **Entity 组织管理**，UI 创建 Entity（名称、类型等必填项，步骤同 EM-E-02）
- 创建成功后，记录该 Entity 的 `entity_id`（可从详情页或列表/接口获取）
- 侧栏进入 **路由管理 → 路由表**，刷新或重新进入列表页
- 按类型筛选 `Entity`，或在属主搜索框输入刚创建的 `entity_id`

预期结果：

- 路由表列表行数较创建前 **+1**（或 `entity` 类型筛选结果 +1）
- 新增行字段：
  - 路由表类型：`Entity`
  - 路由表属主：等于刚创建 Entity 的**名称**
  - 状态：`停用`（默认 `enabled=false`）
- 操作列包含「查看」「启用」「停用」；「启用」可点，「停用」禁用
- 点击「查看」可进入详情，规则列表为空（默认 `rules=[]`）

### 4.2 删除 Entity 后路由表列表减少

**功能模块**：跨模块联动（Entity 组织管理 → 路由表列表）  
**优先级**：P0  
**用例编号**：RT-S-02  
**归属场景**：场景五  
**设计依据**：`ai-gateway-api/model/quota/entity_manager.go`（删除 Entity 时级联删除 `route_rules`）

前置条件：

- 已登录系统
- 存在一个**无下级 Entity、无挂载 API-Key** 的 Entity（若无，先按 RT-S-01 创建）
- 路由表列表中已存在该 Entity 对应的路由表行

测试步骤：

- 记录路由表列表当前行数（或该 `entity_id` 对应行可见）
- 进入 **Entity 组织管理**，删除上述 Entity（确认弹窗点确定，步骤同 EM-E-16）
- 进入 **路由管理 → 路由表**，刷新列表
- 按类型 `Entity` 筛选，或在属主搜索框输入已删除的 `entity_id`

预期结果：

- 路由表列表行数较删除前 **-1**
- 属主为已删除 `entity_id` 的行不再出现
- 按该 `entity_id` 搜索时表格为空或显示「暂无数据」

### 4.5 集群删除被路由规则引用阻止与跳转

**功能模块**：跨模块联动（集群管理 → 路由表规则）  
**优先级**：P0  
**用例编号**：RT-S-05  
**归属场景**：场景五  

前置条件：

- 已登录系统
- 已创建集群 `demo-cluster`
- 在某路由表的规则中引用该集群作为目标

测试步骤：

- 进入集群管理，尝试删除 `demo-cluster`
- 验证删除被阻止
- 验证错误提示包含路由表类型/属主和规则名
- 验证存在「前往处理」链接
- 点击「前往处理」链接，验证跳转到路由规则页

预期结果：

- 删除被阻止，弹窗展示完整引用信息（路由表类型/属主 + 规则名）
- 「前往处理」链接可跳转到对应路由规则页

### 4.6 全链路配置（Entity 类型 → 组织 → API-Key → 路由表）

**功能模块**：跨模块全链路（Entity 类型 + Entity 组织 + API-Key + 路由表）  
**优先级**：P0  
**用例编号**：RT-J-01  
**归属场景**：场景六（@journey）  
**自动化**：`tests/route/test_01_route_cross_module.spec.js`（`serial` + `@journey`）  
**设计依据**：[01 场景六](../01-测试场景概览.md#场景六全链路配置journey)

**与 EM-J-01 的分工**：

| 编号 | 侧重点 |
|------|--------|
| **EM-J-01** | Entity 模块内：类型 → 组织 → API-Key 全生命周期，**不涉及路由表** |
| **RT-J-01** | 在上述链路基础上延伸：**验证路由表联动 + 配置路由规则 + 逆序清理** |

#### 前置条件

- 已登录系统（`globalSetup` + `auth.json`）
- 单条用例内按顺序完成，不依赖其他 spec 残留数据
- 系统中存在至少一个可用集群（用于路由规则目标集群下拉，如 `cluster-01`）
- 失败时 `afterEach` / 用例末尾通过 API 或 UI 清理已追踪资源

#### 测试步骤

全程 **UI 操作**（禁止 API 造数替代创建步骤；清理阶段可用 API 兜底）：

1. **Entity 类型管理**：UI 创建类型（级别 1），搜索确认列表可见（预期同 EM-T-02）
2. **Entity 组织管理**：UI 创建根节点 Entity（挂载步骤 1 的类型），搜索确认可见（预期同 EM-E-02）
3. **路由表列表**：进入路由管理 → 路由表，按属主搜索步骤 2 的 `entity_id`
   - 验证出现 1 条 `Entity` 类型、`停用` 状态的路由表（预期同 RT-S-01）
4. **API-Key 管理**：UI 创建 API-Key，挂载步骤 2 的 Entity（预期同 EM-K-02、EM-K-06）
5. **路由表列表**：刷新列表，按属主搜索步骤 4 的 API-Key `id`
   - 验证出现 1 条 `API-Key` 类型、`停用` 状态的路由表（预期同 RT-S-03）
6. **路由规则详情（Entity）**：在步骤 3 的路由表行点击「查看」→ 进入编辑模式 → 添加 1 条规则：
   - 规则名称：`entity-rule-journey`
   - 表达式：`default_t()`
   - 目标集群：选择已有集群，权重 100
   - 本地保存后点击「提交并生效」（预期同 RT-D-09、RT-D-13）
7. **路由规则详情（API-Key）**：返回列表，在步骤 5 的路由表行点击「查看」→ 同样添加并提交 1 条规则：
   - 规则名称：`apikey-rule-journey`
   - 其余字段同上（预期同 RT-D-09、RT-D-14）
8. **逆序清理**（验证删除联动，预期同 RT-S-04、RT-S-02）：
   - UI 删除步骤 4 的 API-Key → 路由表列表中该 API-Key 行消失
   - UI 删除步骤 2 的 Entity → 路由表列表中该 Entity 行消失
   - UI 删除步骤 1 的类型

#### 预期结果

- 步骤 1~2：Entity 类型、Entity 创建成功
- 步骤 3：路由表列表同步出现 Entity 路由表，默认停用、规则为空
- 步骤 4~5：API-Key 创建成功；路由表列表同步出现 API-Key 路由表
- 步骤 6~7：两条路由表均可成功添加规则并提交生效；返回列表后状态与规则数正确
- 步骤 8：删除 API-Key / Entity 后，路由表对应行同步消失；用例结束时无残留测试数据

#### 测试数据

- **类型名 / Entity 名**：运行时唯一生成（如 `rt-journey-type-{ts}`）
- **API-Key 描述**：`RT-J-01_key_{timestamp}`
- **Entity 规则名**：`entity-rule-journey`
- **API-Key 规则名**：`apikey-rule-journey`
- **表达式**：`default_t()`
- **目标集群**：环境中已有集群（如 `cluster-01`）
- **权重**：100

```bash
npx playwright test tests/route/test_01_route_cross_module.spec.js
```
