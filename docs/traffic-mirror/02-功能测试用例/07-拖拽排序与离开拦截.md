**「有改动分支会回收、无改动分支不回收」——实测不成立（订正）**

- 曾有的推断：有改动退出时会把表格数据整体替换（`rules = cloneDeep(originalRows)` + 重拉集合），行元素被重建，故属性被回收。

- 代码层面两分支路径本就一致：`src/modules/TrafficMirror/index.vue:359-366` 的 `performExitEditMode()` 无论有无改动都执行 `mode='view'` → `rules = cloneDeep(originalRows)` → `fetchRules()`，差别仅在于 `rules` 内容是否与快照相等；而 iView 行 `:key` 取行下标（`node_modules/iview/src/components/table/table-body.vue:11`：`:key="rowKey ? row._rowKey : index"`，`pageTable` 未传 `rowKey`）→ 数据替换前后 key 不变 → 行元素仍是**原地 patch**，不是替换。
- 结论：TM-DR-05 通过的唯一原因是**它没断言该属性**，与「分支差别」无关。

**根因（源码级，可直接定位修复点）**

1. `src/components/table/pageTable.vue:54-55` 把 `:draggable="draggable"`、`@on-drag-drop="onDragDrop"` 透传给 iView `Table`，再逐层下传到 `table-body`（`table-body.vue:9`）与 `table-tr`。
2. `node_modules/iview/src/components/table/table-tr.vue:2-3`：两个分支**同为 `<tr>` 且都不带 `key`**——`v-if="draggable"` 分支带 `draggable` 属性与 `dragstart/drop/dragover` 监听，`v-else` 分支都不带。切换分支时 Vue 的 `sameVnode`（同 tag、key 均为 `undefined`）成立 → **原地 patch 同一个 DOM 元素**，不替换元素。
3. **决定性一环**：`draggable` 属于 Vue 的**枚举型属性**清单——`node_modules/vue/src/platforms/web/util/attrs.ts:22`：`isEnumeratedAttr = makeMap('contenteditable,draggable,spellcheck')`；而 `node_modules/vue/src/platforms/web/runtime/modules/attrs.ts:44-52` 的 `updateAttrs` 清理循环**故意跳过枚举型属性**（`else if (!isEnumeratedAttr(key)) { elm.removeAttribute(key) }`）→ 新 vnode 未携带 `draggable` 时 Vue **不会**执行 `removeAttribute('draggable')`，属性永久残留。写入侧同理走枚举分支（同文件 `:71-72`；`convertEnumeratedValue('draggable', true)` → `'true'`，`util/attrs.ts:28-35`），与实测 `"true"` 一致。
4. 故回收属性只有两条路：**让元素被替换**，或**显式移除属性**。**不能**用「绑定 `draggable="false"`」兜底——那会渲染为 `draggable="false"`（属性仍在、`getAttribute` 不为 `null`），与本文件及 `docs/route-management/02-功能测试用例/02-路由规则详情.md` §2.28 的「行不带 `draggable` 属性」口径不符。
5. 同一 patch 过程还会执行 `updateDOMListeners`（`node_modules/vue/src/core/vdom/helpers/update-listeners.ts:95-100`：新 vnode 未携带某监听时调用 `remove(...)`）→ 残留在元素上的 `dragstart/drop/dragover` **按源码推理已被移除**（待实拖取证，见下）。

### TM-DR-02：拖拽到目标行落到目标行原下标

**功能模块**: 流量镜像规则
**优先级**: P0
**用例编号**: TM-DR-02
**OpenAPI**: `GET /traffic-mirror-rules`（拖拽本身不发请求；提交才走 `PUT /traffic-mirror-rules`）

#### 前置条件

1. 集合内有 ≥3 条规则（自动化为 4 条），已进入编辑模式且已备份快照 `originalRows`。

#### 测试步骤

1. 刚进入编辑模式、未做任何修改时，观察页头「提交并生效」按钮状态。
2. 记录表格当前规则名顺序（基线）。
3. 把第 1 行拖拽到第 3 行上（Playwright 原生 `dragTo`）。
4. 读取重排后的规则名顺序，并再次观察「提交并生效」按钮状态。

#### 预期结果

1. 刚进入编辑模式时本地数组与 `originalRows` 一致（`isDirty` 为 false），「提交并生效」**置灰不可点击**。
2. 拖拽行 A 到行 B = A 移动到 B 的**原下标**处，等价于 `rules.splice(A下标, 1)` 后 `rules.splice(B下标, 0, A)`：基线 `[r0, r1, r2, r3]` 把 r0 拖到 r2 ⇒ `[r1, r2, r0, r3]`。自动化期望值由 `moveRuleToIndex(基线, 0, 2)` 推导，不硬编码规则名。
3. 拖拽产生本地变更后，「提交并生效」由置灰变为**可用**。
4. 拖拽全程**不发后端请求**（无 `PUT /traffic-mirror-rules`）；拖拽只重排本地 `rules`。

#### 测试数据

- mock 规则 4 条（同 TM-DR-01）；账号复用 `conf.json` 的 admin。
- **数据策略**：零后端写入。拖拽只改前端数组，用例结束断言未发出 `PUT`；不用「复制」补齐行数——流量镜像无复制入口，行数由 mock 集合固定提供。

#### 补充说明

- 落点语义由维护者决策：先移除被拖拽行，再按落点行的**原始下标**插入（`src/modules/TrafficMirror/index.vue:412-420` `onRuleDragDrop`）。
- **拖拽后的表格副作用**：`pageTable` 在 `tableData` 变化时会回到第 1 页并清空列搜索 / 列排序条件（与新增/编辑/删除同形，变更记录 §8.2）；本用例不带筛选条件，该副作用无 observable 差异，故未单独断言，其「清空后按新顺序展示全量规则」由 TM-DR-03 覆盖。
- **不重新编号**：三个兄弟模块的行按钮在点击时按 `name` 实时 `findRowIndex(row)`（`src/modules/TrafficMirror/index.vue:329-334`）定位，天然免疫次序变化，因此拖拽后不重编号、也不引入 `index` 字段（变更记录 §7.2）。路由规则页靠客户端 `row.index` 定位，故那边才需要 `refreshRuleIndex()`——「拖拽后每行按钮仍指向该行规则」的逐行断言在路由模块由 RT-D-28 覆盖，本题不做重复覆盖，仅在此说明机制依据。

### TM-DR-03：列排序/列搜索激活时拖拽按源下标移动正确的行

**功能模块**: 流量镜像规则
**优先级**: P1
**用例编号**: TM-DR-03
**OpenAPI**: `GET /traffic-mirror-rules`

#### 前置条件

1. 集合内有 ≥3 条规则（自动化为 4 条），已进入编辑模式。
2. 自动化用的 mock 名称刻意设计：子串 `tm_dr_a` 只命中 2 条（不足全量）；基线顺序既非升序也非降序；且基线首行不是排序极值——这样「按源下标移动」与「按可视下标移动」必然产出不同顺序，负向对照才有区分度。

#### 测试步骤

**列排序态**

1. 点击「规则名」列头的倒序排序图标，记录排序后的可视顺序。
2. 把可视首行拖拽到可视末行上。
3. 读取拖拽后的规则名顺序，与「按源下标派生」的期望顺序比对。
4. 观察「提交并生效」按钮状态与后端请求。

**列搜索态**

5. 在「规则名」列头搜索框输入子串 `tm_dr_a`，确认只展示命中的 2 行。
6. 把可视首行拖拽到可视末行上。
7. 清空列搜索，读取全量规则名顺序并与「按源下标派生」的期望顺序比对。
8. 观察「提交并生效」按钮状态与后端请求。

#### 预期结果

1. 列排序只改变**可视顺序**：排序后的规则名集合与基线一致，但顺序与基线不同。
2. 排序态下拖拽：移动的是**可视首行对应的规则**（源下标经 `baseline.indexOf(可视首行)` 换算），落点是**可视末行对应规则的原下标**——即 `moveRuleToIndex(基线, 可视首行源下标, 可视末行源下标)`。
3. **负向对照**：拖拽结果 ≠ 按可视下标派发的结果 `moveRuleToIndex(基线, 0, 可视末行下标)`；若把源下标当成可视下标派发，移动的将是另一条规则，本项会失败。
4. 列搜索为**纯前端**列内包含匹配（忽略大小写）：输入 `tm_dr_a` 后只展示名称含该子串的 2 行，不触发列表接口请求。
5. 筛选态下拖拽同样按源下标移动正确的行；拖拽后表格按新顺序展示**全量**规则（自动化在拖拽后显式清空一次列搜索再断言）——既不丢行也不串位。`pageTable` 在 `tableData` 变化时本就会清空列搜索 / 列排序条件（变更记录 §8.2），显式清空与之等价。
6. 两种场景下拖拽均属本地变更：「提交并生效」解禁，且无 `PUT /traffic-mirror-rules` 写入。

#### 测试数据

- mock 规则 4 条：`tm_dr_m_mid`（下标 0）、`tm_dr_a_one`（1）、`tm_dr_z_max`（2）、`tm_dr_a_four`（3）。
- 搜索关键字：`tm_dr_a`（命中下标 1 与 3，共 2 条 < 4 条）。
- **数据策略**：零后端写入（同前）。

#### 补充说明

- 源下标派发机制：`pageTable.vue` 维护 `showSrcIndex` / `pageSrcIndex`（展示行 → 源数组下标），列排序（`sortChange`，`src/components/table/pageTable.vue:469-505`）与列搜索（`searchTable`）都同步重排该映射；`onDragDrop`（`src/components/table/pageTable.vue:595-603`）把 `pageSrcIndex[a]` / `pageSrcIndex[b]` 作为 `startIndex` / `endIndex` 派发给页面，因此拖拽在排序/筛选态下不会移动错行。同一文件对 `customSort` 列另有「清空映射、放弃派发」的保护，本模块列均为本地排序，不走该分支。
- 列头搜索定位方式（与实现一致）：自动化 `searchRuleTableByColumn(page, 列标题, 关键字)` 先由列标题换算出列头搜索框的 placeholder（`请输入规则名查询` / `请输入生效条件查询` / `请输入镜像集群查询`，即 `com.tipEnterX` + 列标题 + `com.query`），再复用既有 `searchRulesByColumn(page, placeholder, 关键字)` 填充并回车；关键字传空串即清除筛选。
- 排序定位方式：`sortRuleTableByColumn(page, 列标题, 'desc')` 点击该列头内的 `.ivu-icon-md-arrow-dropdown`（升序为 `.ivu-icon-md-arrow-dropup`）。
