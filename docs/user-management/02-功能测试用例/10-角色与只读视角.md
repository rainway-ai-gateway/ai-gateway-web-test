#### 补充说明（2026-10-16 源码核查）

> **本用例状态：`阻塞`**（2026-10-16 判定）——预期2/3 与产品实现冲突，自动化**按本文档预期原样保留断言**，未迁就实现；详见下方第 3、4 条与证据链。若复跑显示命中行数正常，则本判定撤回、改写为「实为测试侧定位问题（已修）」。

- 筛选控件真实形态：pageTable 的 `searchType: 'select'` 分支渲染的是 **非 filterable** 的 iView Select（`props: { placeholder: $t('com.tipSelectX', {obj: 列标题}), clearable: true, transfer: true }`，`src/components/table/pageTable.vue:158-188`）。iView 的 Select 只在 `filterable` 时才渲染 `<input>`，所以占位文案不是 input 的 `placeholder` 属性，而是 `.ivu-select-placeholder` 文本节点（值 = `请选择角色`）；已选中时同一节点 class 变为 `.ivu-select-selected-value`。自动化定位按真实 DOM 实现。
- **控件值口径**：Select 的 `on-change` 发射的是选项 **value**（iView `publicValue` = `(values[0]||{}).value`，见 `pageTable.vue:175-178`），即 `User.vue:126-129` 里 `searchFilters` 定义的 **枚举** `system_admin` / `system_admin_readonly`（该配置形如 `{label: 中文文案, value: 枚举}`）。该枚举也可在控件隐藏域 `input[type="hidden"]` 的 value 上观察到。
- **预期2/3 与当前实现冲突 → `阻塞`（产品缺陷判定）**：pageTable 前端筛选对「带 `render` 的列」走「渲染文案 ↔ 筛选值」比较（`src/components/table/pageTable.vue:383-402`，核心行 `392`：`displayText = getRenderSearchText(render, itemValue)`，再与 `searchValue` 做 `indexOf`）。角色列的渲染文案是中文（`User.vue:130-133` → `roleLabel()` 返回「系统管理员」/「系统管理员（只读）」），而筛选值是枚举 `system_admin`/`system_admin_readonly`，两者不可能相等 → 选中任一档时命中 **0 行**，与预期2/3「仅命中对应角色行」不符。
  - 实测佐证（2026-10-16 第三轮验证 `report/test-report-20261016-181601.md` 的点击 call log）：下拉项真实 DOM 为 `<li class="ivu-select-item">系统管理员</li>`，即**选项文案 = 渲染文案口径**；而参与比较的 `searchValue` 是枚举 → `indexOf` 恒为 `-1`。
  - 影响面仅限「枚举值 + 中文渲染」的客户端筛选列；服务端分页表的同类下拉走 `on-search-change` 上行筛选值，不受影响。
  - 处置：自动化按本文档预期**原样保留断言**（不迁就实现）。可选修复方向——① select 分支把选中项的 **label** 交给 `searchTable`（与渲染文案口径一致），或 ② 比较时同时接受原始值与渲染文案。
- **测试侧定位问题（已修，与本判定无关）**：本用例先后暴露两个纯测试侧问题，均已修复且不影响预期2/3 的判定——① 角色列筛选控件曾按 `input[placeholder="请选择角色"]` 定位，而 iView 非 filterable Select 不渲染 input（占位是 `.ivu-select-placeholder` 文本）；② 点选下拉项时 `locator.click` 10s 超时（先 `not stable` 后 `not visible`）——触发器点击是开/合切换而 `components/iview/IvuSelect.js` 假设其收起，200ms 的等待短于 iView 0.3s 开合动画，导致「收合动画中仍可见」被误判为已展开而跳过补点。已在 `IvuSelect.js` 改为「以选项是否真的可见为准」的收敛循环，并让 `UserPage.openRoleFilter` 幂等。

### UM-53：只读视角全站巡检（跨模块写入口不变量）

**功能模块**: 角色与只读视角（跨模块巡检）
**优先级**: P0
**用例编号**: UM-53
**OpenAPI**: `GET /open-api/v1/auth/users`（登录态）；巡检本身不发起写请求

#### 前置条件

1. 只读账号 `viewer`（`role=system_admin_readonly`）与管理账号（`conf.json`）均可登录。
2. 产品各模块路由可达（`ai-gateway-web/src/router/router.js`）。`cert` 已于 2026-09-11 随菜单移除，不在巡检范围。

#### 测试步骤

1. 逐条遍历 16 个模块路由（`user` / `providers` / `cluster` / `route-tables` / `ai-cache-rules` / `ai-context-rules` / `traffic-mirror-rules` / `intent-config` / `api-key` / `batches` / `Entity` / `epp` / `model-prices` / `operation-logs` / `security` / `report`）：先以**管理员**口径进入该路由，统计可见写操作入口数量作为基线。
2. 以只读系统管理员登录，重复遍历同一批路由。
3. 每次进入路由后，统计页面内**可见**且文案命中写入口基线的按钮/链接，并检查所有挂 `.v-has-hidden` 的元素。

#### 预期结果

1. 只读视角下每条路由均可达（内容容器可见、URL 未被重定向、无会话异常弹窗）。
2. 只读视角下该路由**可见写操作入口数量为 0**——某个页面或新按钮漏挂 `v-has` 时会在此报出。
3. 只读视角下所有挂 `.v-has-hidden` 的元素，其自身 computed `display` 均为 `none`（既覆盖「挂了 class 但未生效」，也覆盖「有人去掉 `!important` 被 `v-show` 内联样式压过」）。
4. 管理员口径全站可见写入口合计 **> 0**（否则本巡检会空转成假通过），且管理员态下 `.v-has-hidden` 元素数为 **0**（证明该隐藏机制为只读视角专属）。
5. 巡检全程不发起写请求，不修改共享环境数据。

#### 测试数据

1. 只读账号：`viewer`（`role=system_admin_readonly`）
2. 管理账号：`conf.json` 配置账号（`role=system_admin`）
3. 写入口文案基线：`ai-gateway-web/src/i18n/zh.js` 中所有挂 `v-has` 的写控件文案（维护于 `utils/readonly.js` 的 `WRITE_CONTROL_PATTERN`）

#### 补充说明

- **与各模块只读用例的分工**：模块文档负责「本模块哪些按钮该隐、哪些只读入口该留、抽屉是否只读、密钥是否掩码」的细粒度预期；本用例只负责**跨模块不变量**——全站有没有漏网写入口、`v-has` 机制是否仍然生效。二者互补，不重复。
- **环境实测（2026-10-16）**：管理员口径下 `/route-tables`、`/security`、`/operation-logs`、`/report` 的可见写入口均为 0 个。其中 `/operation-logs`、`/report` 本就无写入口（只读页面，断言恒真）；`/route-tables` 因列表默认「状态=启用」筛选而环境内路由表全为停用态（空列表，无行内「启用/停用」按钮）；`/security` 的「触发任务」未出现，原因待 `RS-RO-01` 验证时判定。上述 4 条路由的只读断言不具备区分力，真实覆盖分别由 `RT-RO-01`（显式清空状态筛选）与 `RS-RO-01` 承担。
- 巡检细化到「每条路由一个用例」，因此某条路由失败不影响其余路由继续执行，报告里能直接定位到具体路由。
